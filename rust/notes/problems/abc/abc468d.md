## 問題へのリンク

[ABC468 D - Pre-Palindrome](https://atcoder.jp/contests/abc468/tasks/abc468_d)

## 問題の要約

英小文字列 $S$（$|S| \le 10^4$）の空でない部分文字列（連続）のうち、**1文字以下の書き換えで回文にできる**もの（= 良い文字列）の個数を数える。取り出す位置が違えば別物として数える。

「1文字以下の書き換えで回文」= 両端から対応するペアを見ていったとき、**ミスマッチが1組以下**、と言い換えられる。

## 本番で詰まったところ

考えた方針は「先頭から何文字削るか × 末尾から何文字削るか」の二重ループで部分文字列を全列挙し、それぞれを反転文字列と比べて判定する、というもの。

- 部分文字列の列挙で $O(n^2)$
- **判定がゼロから全ペア比較なので $O(n)$**
- 合計 $O(n^3)$ → 無理

判定が $O(n)$ になるのがボトルネックだと自分で特定できていたのは良い診断だった。**足りなかったのは「判定を差分更新に変える」発想**。

## 方針（O(n²)）

### 1. 制約から目標計算量を逆算する

$n \le 10^4$ は **$O(n^2)$ を狙わせる制約**。$10^8$ に見えるが中心拡張だと実質その半分以下なので Rust なら余裕。
「高度な文字列アルゴリズム（Manacher / suffix array + LCP）を書け」ではなく、**$O(n^3)$ を $O(n^2)$ に落とせ**という問題だった。

### 2. 「削る位置 × 2」ではなく「中心 × 半径」で部分文字列を指定する

回文系は **中心を固定して外側に伸ばす**のが基本形。部分文字列と (中心, 半径) は1対1に対応する。

| | 中心 | 区間 | 中心の個数 |
|---|---|---|---|
| 奇数長 | 文字 `c` そのもの | `[c-k, c+k]` | $n$ |
| 偶数長 | `c` と `c+1` の隙間 | `[c-k+1, c+k]` | $n-1$ |

合わせて $2n-1$ 個の中心 × 半径最大 $n/2$ → $O(n^2)$。

### 3. ミスマッチ数の単調性 → 差分更新できる

中心を固定して半径 $k$ を1ずつ増やすと、増えるペアはちょうど1組。だから

```
（半径 k のミスマッチ数）= （半径 k-1 のミスマッチ数）+ (新しい1ペアが不一致か)
```

**前回の結果に 0 か 1 を足すだけ = 判定が $O(1)$**。これが $n^3 \to n^2$ の本体。

おまけで、ミスマッチ数は $k$ について**単調非減少**なので、2 に達したらそれ以上外に広げても絶対に戻らない → `break` していい。最悪ケース（`aaaa...a`）では効かないが、平均的にはかなり速くなる。

## 実装

```rust
use proconio::input;
use proconio::marker::Bytes;

fn main() {
    input! {
        s: Bytes,
    }
    let n = s.len();
    let mut ans: u64 = 0;

    // 奇数長: 中心 c、半径 k、区間 [c-k, c+k]
    for c in 0..n {
        ans += 1;           // k=0（1文字）は必ず良い文字列
        let mut mism = 0;
        let mut k = 1;
        while k <= c && c + k < n {
            if s[c - k] != s[c + k] {
                mism += 1;
                if mism >= 2 { break; }
            }
            ans += 1;
            k += 1;
        }
    }

    // 偶数長: 中心は c と c+1 の間、区間 [c-k+1, c+k]
    for c in 0..n.saturating_sub(1) {
        let mut mism = 0;
        let mut k = 1;
        while k <= c + 1 && c + k < n {
            if s[c - k + 1] != s[c + k] {
                mism += 1;
                if mism >= 2 { break; }
            }
            ans += 1;
            k += 1;
        }
    }

    println!("{}", ans);
}
```

`ababa` で確認: 奇数側 9（長さ1が5・長さ3が3・長さ5が1、全部 good）＋ 偶数側 4（2文字4つは mism=1 で OK、`abab`/`baba` は mism=2 で break）= **13** ✓

## このセッションで学んだこと

### 回文は「中心 × 半径」で考える（中心拡張法）

回文系のほぼ全ての問題で使う基本形。素朴な中心拡張は Manacher 法の下地でもある。

- 「先頭を何文字削る × 末尾を何文字削る」で列挙すると、各部分文字列がバラバラなので判定を使い回せない
- 「中心固定 + 半径を伸ばす」なら、**1つ前の状態から差分更新できる**
- 「ミスマッチ $k$ 個まで許す」に拡張しても、差分更新できるので素朴展開のまま通ることが多い

**回文が出てきたら、まず「中心 × 半径」で考える。**

知識レベル: 🟢 実装可能

---

### 単調性が嬉しい理由は2つ、本命は「打ち切り」ではなく「差分更新」

半径を伸ばすとミスマッチ数は単調非減少。ここから得られるのは：

1. **差分更新できる**（前の値 + 0か1）→ 判定 $O(n) \to O(1)$ → **これが計算量を落とす本体**
2. 閾値を超えたら `break` できる → 定数倍の高速化（最悪ケースでは効かない）

「単調だから break できる」だけに注目していると、最悪ケースを考えて「結局速くならないのでは」と誤解しがち。効いているのは 1 の方。

知識レベル: 🔵 説明可能

### 制約から目標計算量を逆算する

| $n$ の上限 | 狙う計算量 |
|---|---|
| $10^4$ | $O(n^2)$ でよい |
| $10^5$ 〜 $10^6$ | $O(n \log n)$ / $O(n)$ 必須 |

今回 $n \le 10^4$ という**中途半端に小さい制約**が「$O(n^2)$ 想定」のサイン。詰まったとき「どこまで頑張ればいいか」の指針になる。$10^4$ を見て $O(n \log n)$ を探しにいくと、必要以上に難しい方向へ迷い込む。

知識レベル: 🔵 説明可能（→ [[complexity-estimation]]）

### `String` は添字アクセスできない → `Bytes` で受ける

```rust
let s: String = "abc".to_string();
let c = s[0];   // ← コンパイルエラー
```

Rust の `String` は **UTF-8 のバイト列**。1文字が 1〜4 バイトなので「i 番目の文字」を $O(1)$ で取れない。だから Rust は `s[i]` という API を提供していない（`s[0..3]` の範囲スライスはバイト単位で可能だが、文字境界を跨ぐと panic）。

`String` のままだと `s.chars().nth(i)` になり、これが **$O(i)$**。競プロでは**入力時点で配列に変換してしまう**のが定石。

```rust
input! { s: Bytes }   // s: Vec<u8> になる → s[i] が O(1)
```

`Bytes` は型ではなく **`proconio` のマーカー**（読み方の指示）。実際に入る型は `Vec<u8>`。仲間に `Chars`（`Vec<char>`）、`Usize1`（1-indexed → 0-indexed）。

| マーカー | 型 | 比較 | 備考 |
|---|---|---|---|
| `Bytes` | `Vec<u8>` | `s[i] == b'a'` | メモリ 1/4・速い。ASCII なら基本こっち |
| `Chars` | `Vec<char>` | `s[i] == 'a'` | 見た目が直感的。`char` は 4 バイト固定 |

インデックス計算をしたいときは `Bytes` が楽:

```rust
let idx = (s[i] - b'a') as usize;   // 'a'→0, 'b'→1 … cnt[26] の添字に
```

`Bytes` を使わず自前でもよい（`Bytes` はこの短縮形にすぎない）:

```rust
input! { s: String }
let s = s.into_bytes();                 // Vec<u8>
let s: Vec<char> = s.chars().collect(); // Vec<char>
```

出力で文字列に戻すとき:

```rust
println!("{}", String::from_utf8(v).unwrap());  // Vec<u8> → String
println!("{}", v.iter().collect::<String>());   // Vec<char> → String
```

### 「iter するから O(n)」の切り分けを間違えないこと

本番で「良い文字列判定のために char/iter しないといけない → そこで $O(n)$ 発生 → $n^3$」と考えたが、これは**2つの別問題が混ざっている**。

- **配列にしてしまえば添字アクセスは $O(1)$**。`Bytes`/`Chars` で受ければ、そこはボトルネックにならない
- 真のボトルネックは「**部分文字列ごとにゼロから全ペア比較していたこと**」

「$O(n)$ が発生している」と気づいたら、その $O(n)$ が

1. 要素アクセスの遅さ由来か（→ データ構造を変える）
2. 毎回作り直している計算由来か（→ 差分更新・前計算に変える）

を切り分ける。今回は 2 だった。

知識レベル: 🟢 実装可能

---

### usize のアンダーフローはループ条件で防ぐ

```rust
while k <= c && c + k < n { ... s[c - k] ... }       // 奇数側: c-k >= 0 を保証
while k <= c + 1 && c + k < n { ... s[c - k + 1] ... } // 偶数側: c-k+1 >= 0 を保証
```

Rust の `usize` は負になると panic（debug）/ 巨大値に化ける（release）。`if c - k >= 0` は型的に常に true なので**無意味**。**引き算をする前に条件で守る**のが定石。

知識レベル: 🟢 実装可能

### オーバーフロー

$n = 10^4$ なら部分文字列は約 $5 \times 10^7$ 個。`i32` だと溢れる。`u64` / `i64` で受ける（[[integer-types-overflow]] の $10^9$ ルール）。

知識レベル: 🔵 説明可能

- A・B・C は自力で AC
- D は方針（部分文字列全列挙 + ミスマッチ判定）まで到達したが $O(n^3)$ で断念
