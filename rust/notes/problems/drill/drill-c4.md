## 問題

[[../../../contests/drill/c4|問題文]]

$N$ 個の荷物を順番を変えずに **連続区間** で $K$ 台のトラックに分ける。最も重いトラックの負荷（最大負荷）を最小化したときの値を求める。

## 実装アプローチ

**認識トリガー**: 「**最大を最小化**／最小を最大化」＋「**ある値で可能か？の判定が簡単**」→ **答え（の値域）で二分探索**（パラメトリックサーチ）。

最適化問題を直接解こうとすると詰まるが、

> 「最大負荷が $x$ 以下になるよう $K$ 台以内で分割できるか？」

という **Yes/No 判定**に変換すると簡単（左から貪欲に詰めて、溢れたら次のトラック）。
そして **$x$ を大きくすれば必ず OK 寄りになる（単調性）** ので、OK/NG の境界を二分探索できる。

### 提出したコード

```rust
let ok = |cost: i64| -> bool {
    let mut weight: i64 = 0;
    let mut count: i64 = 1;
    for i in 0..n {
        if weight + w[i] <= cost {
            weight += w[i];
        } else {
            weight = w[i];   // 新トラックに「今の荷物」を載せる（0 ではない！）
            count += 1;
        }
    }
    count <= k as i64
};

let mut lo = *w.iter().max().unwrap(); // 1個も載らない容量は無意味 → 下限は max(w)
let mut hi = w.iter().sum::<i64>();    // 全部1台に積む → 上限は sum(w)
while lo < hi {
    let mid = (lo + hi) / 2;
    if ok(mid) { hi = mid; } else { lo = mid + 1; }
}
println!("{}", lo);
```

## このセッションで学んだこと

### 答えで二分探索（パラメトリックサーチ）のテンプレ

挟み撃ちの形は丸暗記してよい。問題ごとに変わるのは **`ok` の中身** と **`lo`/`hi` の初期値** だけ。

```rust
while lo < hi {
    let mid = (lo + hi) / 2;
    if ok(mid) { hi = mid; }   // OK → もっと小さくできるか試す
    else       { lo = mid + 1; } // NG → mid は不可能なので +1
}
// 終了後 lo == hi が「OK になる最小の x」
```

- `ok(x)` が **x について単調**（境界が1か所）であることが前提
- `lo` の初期値は「絶対に NG な少し手前」or「ありえる最小値」、`hi` は「絶対に OK な値」に取る
- 今回は `lo = max(w)`（1個も載らない容量は判定する意味がない）、`hi = sum(w)`（全部1台＝必ず OK）

🟢 実装可能

### 計算量：log は N の log ではなく「値域」の log

普通の二分探索（ソート済み配列の要素探索）は `log(N)` 回。
でも答えで二分探索は **答えの値の範囲** を割っているので回数は **`log(hi - lo)`**。

- `hi = sum(w)` ≈ $2\times10^5 \times 10^9 = 2\times10^{14}$ → $\log_2(2\times10^{14}) \approx 48$ 回
- 判定 `ok()` が1回 `O(N)`
- 全体 = **`O(N × log(値域))`** ≈ $2\times10^5 \times 48 \approx 10^7$ → 余裕で間に合う

| | 何を探索 | log の中身 |
|---|---|---|
| 普通の二分探索 | 配列の添字 | log(N) |
| 答えで二分探索 | 答えの値域 | log(hi − lo) |

見積もりは **`O(判定の計算量 × log(範囲))`** で覚える。

→ [[abc463c]]（座標が広い時の二分探索）

### `fn` はキャプチャできない → 補助関数はクロージャ(`let`)で書く

`main` の中で `fn ok(...)` と書くと、外側の `n`/`w`/`k` を参照できずコンパイルエラー:

```
error: can't capture dynamic environment in a fn item
       use the `|| { ... }` closure form instead
```

- **`fn`（関数アイテム）** = どこにも属さない独立した関数。**変数を持ち運ぶ箱がない**ので外の変数を覚えられない
- **クロージャ `let ok = |x| {...}`** = 「コード」＋「キャプチャした変数」をセットで包んだもの。だから `n`/`w`/`k` を使える

競プロでは「入力を読んだ後の補助関数」は **クロージャ(`let`)が定番**（毎回引数で渡さなくて済む）。
`fn` を使うのは入力に依存しない純粋計算（`gcd(a,b)` など引数だけで完結するもの）。

```rust
let ok = |cost: i64| -> bool { ... };   // ← この形を覚えておけば実戦は十分
```

🟢 実装可能

### 返り値は「末尾式（セミコロンなし）」

Rust の関数・クロージャは **最後のセミコロンなしの式がそのまま返り値**になる。

```rust
let ok = |cost: i64| -> bool {
    // ...
    count <= k as i64   // ← セミコロンなし＝これが返る
};
```

- `return;` で抜けると `()` を返す → `-> bool` と型が合わずエラー
- `count <= k;` のように **セミコロンを付けると「値を捨てる文」** になり返らない
- `if` / `match` も同じルール（最後の式が値になる）。これを掴むと一気に Rust らしく書ける

🔵 説明可能

### 貪欲の更新ミス：新トラックに「今の荷物」を載せ忘れ

溢れて次のトラックに切り替えるとき、`weight = 0` にすると **今見ている `w[i]` がどこにも積まれない**。
「新しいトラックを使い始める」＝「そのトラックに `w[i]` を最初に載せる」なので正しくは `weight = w[i]`。

```rust
} else {
    weight = w[i];   // ○ 新トラックに今の荷物を載せる
    count += 1;
}
```

🟢 実装可能

## この型の問題のテンプレ

「最大を最小化／最小を最大化」＋「ある値で可能か？の判定が簡単」と来たら **答えで二分探索**。
`ok(x)` を単調になるよう作り、`lo`/`hi` を「必ず NG 側／必ず OK 側」に取って挟み撃ち。
計算量は **判定 O(?) × log(値域)** で見積もる。
